Linux File System

📖 What is this?
The Linux filesystem is a single hierarchical tree starting at / (root). Everything — files, hardware devices, running processes — is accessed as a path in this tree. There is no C:\ or D:\ — just one unified structure.
💡 Why does it matter?
Understanding the Filesystem Hierarchy Standard (FHS) is the most foundational Linux skill. You cannot configure servers, debug issues, write scripts, or manage security without knowing where things live and why.
🏢
Real-world analogy: Think of the Linux filesystem like a large office building. The / (root) is the building itself. /etc is the admin office (settings and configs), /home is the staff area (personal workspaces), /var/log is the security camera recordings (logs), /tmp is the whiteboard (temporary, wiped daily), and /dev is the server room (hardware lives here).

Common Permission Patterns
755
rwxr-xr-x
Standard for directories and executable scripts. Owner has full control, everyone else can read and execute.
644
rw-r--r--
Standard for regular files. Owner can read/write, everyone else can only read. Good for web files.
600
rw-------
Private files. Only the owner can read/write. Required for SSH private keys (~/.ssh/id_rsa).
700
rwx------
Private directory. Only the owner can enter and list it. Used for /root home directory.
777
rwxrwxrwx
⚠️ DANGER: Anyone can read, write, delete. Never use on production. A security vulnerability.
1777
rwxrwxrwt (sticky)
World-writable but sticky bit prevents users deleting each other's files. Used on /tmp.
chmod — Two Ways to Set Permissions
Numeric (Octal) vs Symbolic chmod
Numeric: set all permissions at once
$chmod 755 deploy.sh# Set to rwxr-xr-x directly
$chmod 600 ~/.ssh/id_rsa# SSH key must be private!
Symbolic: add (+), remove (-), set (=) permissions for u/g/o/a
$chmod +x script.sh# Add execute for EVERYONE
$chmod u+x,g-w file# Add exec to user, remove write from group
$chmod o=r file.txt# Set others to read-only EXACTLY
$chmod -R 755 /var/www/# -R applies recursively to all subdirs
📚
Inode analogy: An inode is like a library catalog entry. The actual book (file data) sits on a shelf. The catalog entry (inode) records where the book is, when it was added, how big it is, and who can borrow it. Multiple catalog entries can point to the same book — that\'s a hard link. A Post-it note saying "the book is in room 3B" — that\'s a symbolic link.
What is an Inode?
Inode — The File's ID Card

Every file on Linux has an inode — a data structure that stores everything ABOUT the file except its name and content. The inode number is the file\'s true identity.

Inspect inodes
$stat notes.txt# See full inode info
File: notes.txt
Size: 4096 Blocks: 8 IO Block: 4096
Inode: 2621441 Links: 1
Access: (0644/-rw-r--r--) Uid: (1000/john)
Access: 2026-06-04 10:00:00
Modify: 2026-06-04 09:45:00 # Content changed
Change: 2026-06-04 09:45:00 # Metadata changed
$ls -i notes.txt# Quick inode number
2621441 notes.txt

The inode stores: permissions, owner UID/GID, file size, timestamps (atime/mtime/ctime), and pointers to the actual data blocks on disk. The filename is stored separately in the directory, not the inode itself.

Hard Links vs Soft Links — Side by Side
🔗 Hard Link
ln original.txt hardlink.txt

  • Points directly to the same inode
  • Deleting original? File still exists via hard link
  • Both names show identical content
  • Cannot span different filesystems/partitions
  • Cannot hard-link directories
  • Link count in inode goes up by 1
🔗 Symbolic (Soft) Link
ln -s /path/original symlink

  • Stores the path to the target
  • Delete original? Link breaks (dangling symlink)
  • Has its own inode, tiny file
  • Can cross filesystems and partitions
  • Can link to directories
  • Use readlink -f to follow the chain
Hands-on: Creating and inspecting links
$echo "hello" > original.txt
$ln original.txt hardlink.txt# Create hard link
$ln -s original.txt softlink.txt# Create soft link
$ls -li *.txt# -i shows inode numbers
2621441 -rw-r--r-- 2 john 6 hardlink.txt ← same inode as original!
2621441 -rw-r--r-- 2 john 6 original.txt ← link count = 2
2621889 lrwxrwxrwx 1 john 12 softlink.txt -> original.txt ← different inode, shows target
$readlink -f softlink.txt# Resolve to real path
/home/john/original.txt
$rm original.txt# Delete original
$cat hardlink.txt# Hard link: still works!
hello
$cat softlink.txt# Soft link: broken!
cat: softlink.txt: No such file or directory
📡
Real-world symlink example: On modern Ubuntu, /bin is actually a symlink to /usr/bin. Run ls -la /bin and you\'ll see /bin -> usr/bin. Similarly, /lib -> usr/lib. This is how the OS consolidates the legacy directory structure.
👑
Ownership analogy: Every file has a owner (an individual person) and a group (a team). Like a document that belongs to "Alice" and is shared with the "developers" team. Others not in that team can only view it based on the "others" permission bits.
chown — Change Ownership
chown examples
$ls -la app.py
-rw-r--r-- 1 root root 1024 Jun 04 app.py
Change owner to john, group to developers:
$sudo chown john:developers app.py
$ls -la app.py
-rw-r--r-- 1 john developers 1024 Jun 04 app.py
Change only owner (keep group):
$sudo chown alice app.py
Change only group:
$sudo chgrp www-data /var/www/html/
Recursively change entire directory tree:
$sudo chown -R john:developers /var/www/myapp/
Common Ownership Patterns in Production
Web Server Files (Nginx/Apache)
$ls -la /var/www/html/
-rw-r--r-- 1 www-data www-data 4096 index.html
Nginx runs as 'www-data' user. Files it needs to read must be owned by or readable to www-data.
$sudo chown -R www-data:www-data /var/www/html/
$sudo chmod -R 755 /var/www/html/
SSH Private Key — Strict Permissions Required
$ls -la ~/.ssh/
drwx------ 2 john john 60 . ← 700: dir private
-rw------- 1 john john 411 id_ed25519 ← 600: private key
-rw-r--r-- 1 john john 98 id_ed25519.pub ← 644: public key
SSH will REFUSE to use your key if permissions are too open!
$chmod 700 ~/.ssh/ && chmod 600 ~/.ssh/id_ed25519
⚠️
Never run web apps as root! If a web app running as root gets hacked, the attacker has full system access. Always create a dedicated user (e.g., www-data, appuser) with minimal permissions. This is called the principle of least privilege.

💡 Why does it matter?
Provisioning servers, setting up databases, and adding disk space all require understanding partitioning, formatting, and /etc/fstab persistent mounts.
