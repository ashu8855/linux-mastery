Linux File System

📖 What is this?
The Linux filesystem is a single hierarchical tree starting at / (root). Everything — files, hardware devices, running processes — is accessed as a path in this tree. There is no C:\ or D:\ — just one unified structure.
💡 Why does it matter?
Understanding the Filesystem Hierarchy Standard (FHS) is the most foundational Linux skill. You cannot configure servers, debug issues, write scripts, or manage security without knowing where things live and why.
🏢
Real-world analogy: Think of the Linux filesystem like a large office building. The / (root) is the building itself. /etc is the admin office (settings and configs), /home is the staff area (personal workspaces), /var/log is the security camera recordings (logs), /tmp is the whiteboard (temporary, wiped daily), and /dev is the server room (hardware lives here).

Common Permission Patterns
755
rwxr-xr-x
Standard for directories and executable scripts. Owner has full control, everyone else can read and execute.
644
rw-r--r--
Standard for regular files. Owner can read/write, everyone else can only read. Good for web files.
600
rw-------
Private files. Only the owner can read/write. Required for SSH private keys (~/.ssh/id_rsa).
700
rwx------
Private directory. Only the owner can enter and list it. Used for /root home directory.
777
rwxrwxrwx
⚠️ DANGER: Anyone can read, write, delete. Never use on production. A security vulnerability.
1777
rwxrwxrwt (sticky)
World-writable but sticky bit prevents users deleting each other's files. Used on /tmp.
chmod — Two Ways to Set Permissions
Numeric (Octal) vs Symbolic chmod
Numeric: set all permissions at once
$chmod 755 deploy.sh# Set to rwxr-xr-x directly
$chmod 600 ~/.ssh/id_rsa# SSH key must be private!
Symbolic: add (+), remove (-), set (=) permissions for u/g/o/a
$chmod +x script.sh# Add execute for EVERYONE
$chmod u+x,g-w file# Add exec to user, remove write from group
$chmod o=r file.txt# Set others to read-only EXACTLY
$chmod -R 755 /var/www/# -R applies recursively to all subdirs
📚
Inode analogy: An inode is like a library catalog entry. The actual book (file data) sits on a shelf. The catalog entry (inode) records where the book is, when it was added, how big it is, and who can borrow it. Multiple catalog entries can point to the same book — that\'s a hard link. A Post-it note saying "the book is in room 3B" — that\'s a symbolic link.
What is an Inode?
Inode — The File's ID Card

Every file on Linux has an inode — a data structure that stores everything ABOUT the file except its name and content. The inode number is the file\'s true identity.

Inspect inodes
$stat notes.txt# See full inode info
File: notes.txt
Size: 4096 Blocks: 8 IO Block: 4096
Inode: 2621441 Links: 1
Access: (0644/-rw-r--r--) Uid: (1000/john)
Access: 2026-06-04 10:00:00
Modify: 2026-06-04 09:45:00 # Content changed
Change: 2026-06-04 09:45:00 # Metadata changed
$ls -i notes.txt# Quick inode number
2621441 notes.txt

The inode stores: permissions, owner UID/GID, file size, timestamps (atime/mtime/ctime), and pointers to the actual data blocks on disk. The filename is stored separately in the directory, not the inode itself.

Hard Links vs Soft Links — Side by Side
🔗 Hard Link
ln original.txt hardlink.txt

  • Points directly to the same inode
  • Deleting original? File still exists via hard link
  • Both names show identical content
  • Cannot span different filesystems/partitions
  • Cannot hard-link directories
  • Link count in inode goes up by 1
🔗 Symbolic (Soft) Link
ln -s /path/original symlink

  • Stores the path to the target
  • Delete original? Link breaks (dangling symlink)
  • Has its own inode, tiny file
  • Can cross filesystems and partitions
  • Can link to directories
  • Use readlink -f to follow the chain
Hands-on: Creating and inspecting links
$echo "hello" > original.txt
$ln original.txt hardlink.txt# Create hard link
$ln -s original.txt softlink.txt# Create soft link
$ls -li *.txt# -i shows inode numbers
2621441 -rw-r--r-- 2 john 6 hardlink.txt ← same inode as original!
2621441 -rw-r--r-- 2 john 6 original.txt ← link count = 2
2621889 lrwxrwxrwx 1 john 12 softlink.txt -> original.txt ← different inode, shows target
$readlink -f softlink.txt# Resolve to real path
/home/john/original.txt
$rm original.txt# Delete original
$cat hardlink.txt# Hard link: still works!
hello
$cat softlink.txt# Soft link: broken!
cat: softlink.txt: No such file or directory
📡
Real-world symlink example: On modern Ubuntu, /bin is actually a symlink to /usr/bin. Run ls -la /bin and you\'ll see /bin -> usr/bin. Similarly, /lib -> usr/lib. This is how the OS consolidates the legacy directory structure.
👑
Ownership analogy: Every file has a owner (an individual person) and a group (a team). Like a document that belongs to "Alice" and is shared with the "developers" team. Others not in that team can only view it based on the "others" permission bits.
chown — Change Ownership
chown examples
$ls -la app.py
-rw-r--r-- 1 root root 1024 Jun 04 app.py
Change owner to john, group to developers:
$sudo chown john:developers app.py
$ls -la app.py
-rw-r--r-- 1 john developers 1024 Jun 04 app.py
Change only owner (keep group):
$sudo chown alice app.py
Change only group:
$sudo chgrp www-data /var/www/html/
Recursively change entire directory tree:
$sudo chown -R john:developers /var/www/myapp/
Common Ownership Patterns in Production
Web Server Files (Nginx/Apache)
$ls -la /var/www/html/
-rw-r--r-- 1 www-data www-data 4096 index.html
Nginx runs as 'www-data' user. Files it needs to read must be owned by or readable to www-data.
$sudo chown -R www-data:www-data /var/www/html/
$sudo chmod -R 755 /var/www/html/
SSH Private Key — Strict Permissions Required
$ls -la ~/.ssh/
drwx------ 2 john john 60 . ← 700: dir private
-rw------- 1 john john 411 id_ed25519 ← 600: private key
-rw-r--r-- 1 john john 98 id_ed25519.pub ← 644: public key
SSH will REFUSE to use your key if permissions are too open!
$chmod 700 ~/.ssh/ && chmod 600 ~/.ssh/id_ed25519
⚠️
Never run web apps as root! If a web app running as root gets hacked, the attacker has full system access. Always create a dedicated user (e.g., www-data, appuser) with minimal permissions. This is called the principle of least privilege.

Linux User Management

📖 What is this?
Linux is a multi-user operating system. Every file, process, and resource has an owner. Users are identified by a numeric UID, belong to groups, and access is controlled entirely by those identities.
💡 Why does it matter?
Every server you ever manage will require creating service accounts, granting sudo access, and locking down permissions. Get this wrong and you either lock yourself out or leave the system wide open.
🏢
Think of it like an office building: Each person has an employee badge (UID). Badges belong to departments (groups). Some doors need a specific badge, others need you to be in a certain department. The security guard (root / sudo) can open any door — but you should only use that power when truly necessary.

Reading the Full File
Exploring /etc/passwd
$cat /etc/passwd# View all accounts
$grep john /etc/passwd# Find a specific user
$getent passwd john# NSS-aware lookup (works with LDAP/NIS too)
john:x:1000:1000:John Doe:/home/john:/bin/bash
$awk -F: '$3 >= 1000' /etc/passwd# List only human users (UID ≥ 1000)
$cut -d: -f1 /etc/passwd# List only usernames
System Accounts vs Human Users
🤖 System Accounts (UID 0–999)
Created by the OS and packages. Examples: root (UID 0), www-data (web server), postgres (database), nobody (minimal privileges). Shell is usually /usr/sbin/nologin or /bin/false — they cannot log in interactively.
👤 Human Users (UID 1000+)
Created by sysadmins for actual people. Have a real home directory like /home/username, a working shell like /bin/bash, and usually belong to supplementary groups for additional access.
🔐
Why shadow exists: Originally /etc/passwd stored password hashes. Since it was world-readable, attackers could download it and run offline dictionary attacks. Shadow was invented to move hashes to a root-only file. The "x" in passwd just says "the real data is in shadow".
/etc/shadow — Field-by-Field Decoder
Password Hash Format Explained
Hash anatomy
$6$ algorithm · rAnD0mSaLt salt · XxXxXxXxXxXxXxXxXxXxXx… hashed password
Algorithm IDs: $1$ = MD5 (weak, avoid) · $5$ = SHA-256 · $6$ = SHA-512 (current standard) · $y$ = yescrypt (modern Ubuntu)
Password Aging with chage
chage — Password aging policy
$sudo chage -l john# View john's full password aging info
Last password change : Jun 01, 2026
Password expires : Sep 01, 2026
Password inactive : never
Account expires : never
Minimum number of days : 0
Maximum number of days : 90
Number of days of warning : 7
$sudo chage -M 90 john# Set max 90-day expiry
$sudo chage -W 7 john# Warn 7 days before expiry
$sudo chage -m 1 john# Minimum 1 day between changes
$sudo chage -E 2027-01-01 john# Account expires on this date
$sudo passwd -e john# Force change on next login
⚠️
/etc/shadow permissions: This file must be 640 (root:shadow) or 000. If it becomes world-readable, attackers can download password hashes and crack them offline. Check with: ls -la /etc/shadow
Creating Users
🔧 useradd (Universal)
Low-level C binary. Available on ALL Linux distros. Needs explicit flags — won't create home dir or set shell by default without them.
#useradd -m -s /bin/bash -c "John Doe" john
-m = create home · -s = shell · -c = comment
#passwd john# MUST set password separately!
#useradd -r -s /usr/sbin/nologin appuser
-r = system account (UID < 1000, no home)
🧙 adduser (Debian/Ubuntu)
Friendly interactive script. Automatically creates home, copies /etc/skel, prompts for password and full name. Preferred for interactive admin work.
#adduser john
Adding user 'john' ...
New password: ••••••••
Full Name []: John Doe
Is the information correct? [Y/n] Y
Modifying Users — usermod
usermod — Modify existing user
#usermod -aG docker john# Add john to docker group (KEEP existing groups!)
#usermod -s /bin/zsh john# Change login shell
#usermod -d /home/john2 -m john# Move home dir
#usermod -l newname john# Rename login name
#usermod -L john# Lock account
#usermod -U john# Unlock account
#usermod -e 2027-12-31 john# Set account expiry date
⚠️
-aG vs -G trap! usermod -G docker john (without -a) REPLACES all supplementary groups with just "docker". John loses access to sudo, www-data, and every other group. Always use -aG (append + groups) to add a group without removing existing ones.
Deleting Users
userdel — Remove user account
#userdel john# Remove account but KEEP home dir (files remain)
#userdel -r john# Remove account AND delete home + mail spool
#find / -user john 2>/dev/null# Find orphaned files after deletion
#find / -nouser 2>/dev/null# Find files with no valid owner
Switching Users
su — Substitute User
$su john# Switch to john — keeps YOUR environment vars
$su - john# Full login shell — loads john's .bashrc, HOME, PATH
$su -# Become root with root's full environment
$sudo -i# Preferred: root login shell via sudo
$sudo -u john ls /home/john# Run single command as john
$exit# Return to your original user
👥
Groups analogy: Think of groups like access cards for different floors. Being in the docker group lets you run Docker. Being in sudo lets you run admin commands. Being in www-data lets you write web files. One person can have many cards — but each door only opens if you have the right one.
Primary Group vs Supplementary Groups
Primary Group (GID)
Every user has exactly one primary group, stored in /etc/passwd. New files created by the user are owned by this group by default. Usually a group with the same name as the user (private user group pattern).
Supplementary Groups
Additional groups for extra access. A user can be in many supplementary groups. These are stored in /etc/group. Examples: sudo, docker, audio, video, www-data. Changes take effect on next login.
/etc/group Format
/etc/group — Decoded
Reading /etc/group
$cat /etc/group | grep john# All groups john is in
$getent group sudo# Who is in the sudo group?
sudo:x:27:ubuntu,john,alice
$groups john# All groups for john (quick view)
john : john sudo docker www-data
$id john# Full UID + GID + all groups with numbers
uid=1000(john) gid=1000(john) groups=1000(john),27(sudo),998(docker),33(www-data)
Managing Groups
groupadd / gpasswd / groupdel
#groupadd developers# Create new group
#groupadd -g 1500 developers# Create with specific GID
#gpasswd -a john developers# Add john to developers
#gpasswd -d john developers# Remove john from developers
#gpasswd -M john,alice,bob developers# Set exact member list
#groupdel developers# Delete group (fails if it's a primary group)
#groupmod -n devteam developers# Rename group
💡
Group changes need re-login! When you add yourself to a group with usermod -aG or gpasswd -a, the change doesn't take effect in your current session. You must log out and log back in. Or use newgrp groupname to activate the group immediately in the current shell without re-logging in.
🛡️
sudo vs su — key difference: su says "become another user". sudo says "run THIS ONE COMMAND with elevated privileges, then return to being yourself". sudo logs every command, requires YOUR OWN password (not root's), and can be scoped to specific commands — making it far more auditable and secure.
How sudo Works
sudo basics
$sudo apt update# Run one command as root
$sudo -i# Open a root login shell (use sparingly)
$sudo -u www-data ls /var/www# Run as a specific user
$sudo -l# List what YOU are allowed to do
User john may run the following commands:
(ALL : ALL) ALL
$sudo -k# Invalidate sudo timestamp (re-ask password next time)
The sudoers File — /etc/sudoers
🔑
Always use visudo to edit this file. It syntax-checks before saving. A broken sudoers file can lock everyone out of sudo — requiring single-user mode recovery to fix.
sudoers Rule Syntax Explained
FORMAT: who where=(as_whom) what
# Full sudo access for user john
john ALL=(ALL:ALL) ALL
# All members of sudo group can run all commands
%sudo ALL=(ALL:ALL) ALL
# john can restart nginx without a password
john ALL=(root) NOPASSWD: /bin/systemctl restart nginx
# Deploy user can only run specific deploy script
deploy ALL=(root) NOPASSWD: /opt/scripts/deploy.sh
% prefix = group · ALL = any host · (ALL:ALL) = run as any user:group · NOPASSWD = no password prompt
Drop-in sudoers Files — Best Practice
/etc/sudoers.d/ — safer than editing sudoers directly
# Instead of editing /etc/sudoers, create small files in /etc/sudoers.d/
#visudo -f /etc/sudoers.d/john
# Contents:
john ALL=(root) NOPASSWD: /bin/systemctl restart nginx
#chmod 440 /etc/sudoers.d/john# sudoers files must be 440
# This is safer — a mistake only affects this file, not the whole sudoers

Linux Process Management

📖 What is this?
Every running program is a process — a live instance of a program with its own PID (Process ID), memory space, owner, and file descriptors. Processes can spawn children, be paused, killed, or shuffled between the foreground and background.
💡 Why does it matter?
As a developer or sysadmin you constantly face: a server is slow — which process is eating CPU? An app crashed — what was its exit code? A port is in use — what process owns it? This module gives you every tool to answer those questions.
🏭
Analogy: Think of Linux as a factory. The kernel is the factory manager. Each process is a worker with a badge number (PID). Workers can spawn apprentices (child processes). You can pause a worker (Ctrl+Z), fire them (kill), or tell them to stop when convenient (SIGTERM). The ps and top commands are your factory floor dashboard.

Process States
R
Running / Runnable
Actively using CPU, or in the run queue waiting for its turn. Healthy and busy.
S
Sleeping (interruptible)
Waiting for an event (network data, user input, timer). Wakes up when interrupted. Most idle processes are here.
D
Uninterruptible Sleep
Waiting for hardware I/O (disk read). Cannot be killed. If stuck here: bad disk or NFS mount. Reboot may be required.
T
Stopped
Paused by Ctrl+Z (SIGTSTP) or SIGSTOP. Frozen — not using CPU. Resume with fg or bg.
Z
Zombie
Process finished but parent has not read its exit code yet. Holds no resources. Many zombies = parent process bug.
I
Idle (kernel thread)
Kernel thread in uninterruptible sleep but considered idle. Shown in modern kernels for kernel workers.
Linux Signals — Talking to Processes
📡
Signals analogy: Signals are like notifications sent to a process. SIGTERM is a polite "please stop when you're ready." SIGKILL is the kernel forcefully terminating — the process has no say. SIGHUP was originally "your terminal hung up" but daemons repurpose it as "reload your config."
Important signals — kill -l to list all 64
NUM NAME MEANING / USE 1SIGHUPTerminal closed OR reload config (nginx -s reload sends this) 2SIGINTCtrl+C — interrupt request from keyboard 3SIGQUITCtrl+\ — quit and dump core file for debugging 9SIGKILL⚠️ Instant forced termination — cannot be caught or ignored 15SIGTERMPolite termination request — process can clean up first 17SIGCHLDChild process stopped/exited — sent to parent automatically 18SIGCONTContinue a stopped process (what bg/fg send) 19SIGSTOPPause process — like Ctrl+Z but cannot be caught or ignored 20SIGTSTPCtrl+Z — suspend to background (process CAN catch this)
$kill -15 1234# SIGTERM — try this first
$kill -9 1234# SIGKILL — only if SIGTERM fails
$kill -1 1234# SIGHUP — reload config without restart
$kill -l# List all 64 signal names and numbers
🏆
Best practice kill order: (1) kill -15 PID — wait 5 seconds — (2) kill -9 PID. Never jump straight to -9. SIGKILL gives no chance for the process to flush buffers, close database connections, or write final log entries. Data corruption is possible.
📋
ps (process status) is a snapshot — like taking a photo of the factory floor right now. It does not update. For a live video, use top or htop. ps aux is the most commonly used form — memorise it.
ps aux — Column by Column

Common ps Patterns
Real-world ps usage

$ps aux --sort=-%cpu | head -10# Top 10 CPU-hungry processes
$ps aux --sort=-%mem | head -10# Top 10 memory consumers
$ps aux --forest# Parent-child tree (who spawned what)
$ps -ef | grep defunct# Find zombie processes
$ps -u www-data# All processes owned by www-data
pgrep — scripting-friendly process lookup
$pgrep nginx# Just the PID(s) — great for scripts
$pgrep -l nginx# PID + name
$pgrep -u john python# john's python processes
$if pgrep nginx > /dev/null; then echo "nginx is running"; fi

Foreground vs Background: In your shell, only ONE process runs in the foreground at a time — it owns your keyboard. Background processes run silently without your keyboard. You can have many background jobs. The shell tracks them with job numbers like [1], [2].
Job Control Flow
Complete job control workflow
$sleep 100# Running in foreground — blocks terminal
↓ Press Ctrl+Z to suspend it
[1]+ Stopped sleep 100
$bg# Resume the most recent job in background
[1]+ sleep 100 &
$sleep 200 &# Start another process directly in background
[2] 3456
$jobs# List all background/suspended jobs
[1]- Running sleep 100 &
[2]+ Running sleep 200 &
$fg %2# Bring job 2 back to foreground
$kill %1# Kill job 1 by job number (not PID)
Surviving Terminal Closure — nohup, disown, screen, tmux
Keep processes alive after logout
nohup — simplest approach, output saved to nohup.out
$nohup ./long_script.sh &
nohup: ignoring input and appending output to 'nohup.out'
$nohup ./script.sh > output.log 2>&1 &# Custom log file
disown — detach an already-running background job
$./script.sh &# Start in background
$disown %1# Remove from job table — now immune to logout
$disown -a# Disown ALL background jobs at once
tmux — best for interactive sessions you need to resume
$tmux new -s mysession# Create named session
$tmux detach# or Ctrl+B then D — detach (still running!)
$tmux attach -t mysession# Reconnect from anywhere
$tmux ls# List all tmux sessions
🏆
Production recommendation: For long-running tasks on remote servers, always use tmux or screen. If your SSH connection drops mid-task, nohup keeps it running but you lose the interactive output. With tmux, you just re-attach and pick up exactly where you left off.

Nice analogy: Imagine five workers sharing one printer. The "niceness" value determines how politely each worker waits. A very nice worker (high nice value = +19) steps aside for everyone else. A selfish worker (low nice value = -20) cuts to the front of the line. The kernel uses this to schedule CPU time.

nice and renice
nice — set priority when STARTING a process
$nice -n 10 ./backup.sh# Low priority — won't slow down other work
$nice -n 19 tar -czf backup.tar.gz /home/# Minimum priority for backup
$sudo nice -n -10 ./critical.sh# High priority (root needed for negative)
renice — change priority of a RUNNING process
$renice +15 -p 1234# Lower priority of PID 1234
$sudo renice -5 -p 1234# Boost priority (root needed)
$renice +10 -u john# Lower priority of ALL john's processes
Check current niceness in ps output (NI column)
$ps -o pid,ni,cmd -p 1234
PID NI CMD
1234 10 ./backup.sh
💡
When to use nice: Run backups, video encoding, large compilations, and database dumps with nice -n 15 or higher. This lets your server stay responsive for users while the heavy job runs in the background without competing for CPU.

lsof (List Open Files) is one of the most powerful diagnostic tools. Since everything in Linux is a file — including network sockets, pipes, and devices — lsof can answer: "Who is using port 80?", "Why can't I unmount this disk?", "What files does this process have open?"
lsof — Common Real-World Uses
lsof diagnostic patterns
Network / Port investigation
$sudo lsof -i :80# Who owns port 80? (resolve port conflict)
$sudo lsof -i :3306# Is MySQL actually listening?
$sudo lsof -i TCP:80 -i TCP:443# Both HTTP and HTTPS
$sudo lsof -i -n -P# All network connections (numeric, no DNS)
Process file inspection
$lsof -p 1234# Every file open by PID 1234
$lsof -u john# All files opened by user john
$lsof +D /var/log/nginx/# Who has files open in this directory?
$lsof /dev/sdb1# Why can't I unmount? Find who's using the disk
Deleted-but-open files (common disk space mystery!)
$lsof | grep deleted# Files deleted but still held open by a process
nginx 1024 www-data 4w REG 8,1 2147483648 /var/log/access.log (deleted)
This is why df shows disk full but du doesn't — the space is held by a running process. Fix: restart the process (nginx reload) to release the file handle.
/proc — The Process Filesystem
🧠
Every running process has a directory at /proc/PID/. This is a virtual filesystem — the kernel generates it in memory, nothing is on disk. It is the raw source of information that ps, top, and lsof all read from.
/proc/PID directory contents
$ls /proc/1234/
cmdline cwd environ exe fd/ maps mem net/ stat status task/
$cat /proc/1234/status# State, memory, UID, threads
Name: nginx
State: S (sleeping)
Pid: 1234   PPid: 1 ← parent PID
VmRSS: 57344 kB ← actual RAM used
Threads: 4
